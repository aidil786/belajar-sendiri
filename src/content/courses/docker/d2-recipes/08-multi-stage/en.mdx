A **<Term id="multi-stage-build">multi-stage build</Term>** has two kitchens. The `build` stage cooks with Node. The last stage starts fresh from nginx. `COPY --from=build` carries over only the dish: `dist/`.
</Card>

<Card id="try-order" type="try">
Put this two-stage recipe in order.

<Interactive name="OrderList" items={['FROM node:24-alpine AS build', 'RUN npm ci', 'RUN npm run build', 'FROM nginx:1.30-alpine', 'COPY --from=build /src/dist/ /usr/share/nginx/html/']} label="First line at the top" success="Cook first, then a fresh stage takes only the dish." />

<Hint>Each stage starts with its own FROM. Cook before you serve.</Hint>
</Card>

<Card id="try-target" type="try">
Build only the cooking stage as `kedai:build`. Then build the full recipe as `kedai:1.0`. Compare their sizes.

<Interactive name="KitchenSim" scenario="d2-l08" goal={{ imageExists: ['kedai:build', 'kedai:1.0'], lastTyped: '^docker images' }} hints={['Type docker build --target build -t kedai:build .', 'Then docker build -t kedai:1.0 .', 'Then docker images kedai']} success="Same recipe. <Hint>`--target build` stops after the stage called `build`.</Hint>

<Card id="check-npm" type="check">

`which npm` finds nothing in `kedai:1.0`. In the build stage, npm is there. Diners never see the kitchen.
</Card>

<Card id="win" type="win">
You can now cook in one stage and ship only the dish.
</Card>

<Card id="deeper" type="deeper">
Stages without a name are called by number: `COPY --from=0`. Names are clearer. `COPY --from` can also copy from any image, like `--from=nginx:1.30-alpine`. Fewer tools in the final image also means fewer security holes.
