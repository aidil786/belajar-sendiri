A **<Term id="monorepo">monorepo</Term>** keeps many projects in one repo. Each project gets its own folder. One PR can change them all at once.
</Card>

<Card id="try-sort" type="try">
Both ways have wins. Sort each win to its side.

<Interactive name="SortCards" buckets={[{ id: 'mono', label: 'One monorepo' }, { id: 'many', label: 'Many repos' }]} items={[{ label: 'One PR changes the web and the app together', bucket: 'mono', why: 'Everything is in one repo, so one PR is enough.' }, { label: 'Each repo has its own access list', bucket: 'many', why: 'On GitHub, you give people access repo by repo.' }, { label: 'Shared code lives in one place', bucket: 'mono', why: 'Every project uses the same copy.' }, { label: 'Each repo stays small and quick to clone', bucket: 'many', why: 'A small repo downloads fast.' }, { label: 'One set of tools and checks for everything', bucket: 'mono', why: 'Set them up once, for every project.' }, { label: 'Each project has its own short history', bucket: 'many', why: 'The log only shows that one project.' }]} success="Sorted! <Hint>Together and in sync? Monorepo. Separate and private? Many repos.</Hint>

<Card id="predict" type="predict">

<Card id="win" type="win">
You can now choose between one big repo and many.
</Card>

<Card id="deeper" type="deeper">
Huge monorepos can get slow. Git has helpers. `git sparse-checkout` fills in only the folders you need. A partial clone skips old file versions until you need them. A CODEOWNERS file can name owners for each folder. World 10 goes deeper.
</Card>
