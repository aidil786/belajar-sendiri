<Card id="try-sort" type="try">

<Card id="predict" type="predict">
Outage at 3am. You fix it by clicking in the cloud console. What should happen the next morning?

<Interactive name="Choice" options={[{ label: 'Put the fix in the blueprint, then plan shows No changes', correct: true, why: 'Otherwise the next apply quietly undoes your fix.' }, { label: 'Nothing: it works now', why: 'The blueprint still says the old thing. </Card>

<Card id="check-order" type="check">
Put the after-emergency steps in order.

<Interactive name="OrderList" items={['Fix the outage first', 'Write down what you clicked', 'Put it in the blueprint, or adopt it with an import block', 'Plan: it should say No changes', 'Merge it, with a review']} label="First step at the top" success="Clicking is fine in a fire. Writing it down keeps it." />
</Card>

<Card id="check" type="check">
Swipe: a good habit, or needs work?

<Interactive name="SwipeJudge" prose cards={[{ text: 'Blueprint the things you would hate to rebuild by hand', good: true, why: 'That is where IaC pays off most.' }, { text: 'Manage one database from two tools at once', good: false, why: 'They undo each other. Pick one owner.' }, { text: 'Click in an emergency, then write it down the next day', good: true, why: 'Safe now, tidy later.' }, { text: 'Put every database row into OpenTofu', good: false, why: 'Rows change all day. IaC is for the building, not the stock.' }]} />
</Card>

<Card id="win" type="win">
You can now choose when a blueprint helps, and when it gets in the way.
</Card>

<Card id="deeper" type="deeper">
IaC is great for things that last, repeat or need review. It is weak for data and very short experiments. It also clashes with things another tool owns, like a Deployment managed by Argo CD. One owner per thing is the rule.
</Card>
