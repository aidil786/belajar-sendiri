<Card id="see-versions" type="see">
<Interactive name="KubeReplay" scenario="k1-empty" commands={['kubectl version', 'kubectl get nodes']} label="kubectl version shows Client v1.37.2 and Server v1.37.0. All three nodes run v1.37.0." />

Your kubectl, the API server and each stall's kubelet all have versions. **<Term id="version-skew">Version skew</Term>** is how far apart they may be and still work together.
</Card>

<Card id="try-skew" type="try">
The API server runs 1.37. Which parts are close enough?

<Interactive name="SortCards" buckets={[{ id: 'ok', label: 'Allowed' }, { id: 'no', label: 'Too far apart' }]} items={[{ label: 'kubelet 1.34', bucket: 'ok', why: 'A kubelet may be up to 3 minors older.' }, { label: 'kubelet 1.38', bucket: 'no', why: 'A kubelet must never be newer than the API server.' }, { label: 'kubectl 1.38', bucket: 'ok', why: 'kubectl may be one minor older or newer.' }, { label: 'kubectl 1.35', bucket: 'no', why: 'Two minors older is too far for kubectl.' }, { label: 'kube-scheduler 1.36', bucket: 'ok', why: 'It may be one minor older, never newer.' }]} success="Sorted! The API server leads. Others may trail a little." />
</Card>

<Card id="see-order" type="see">
So the API server goes first, and stalls follow. Put a minor upgrade in order.

<Interactive name="OrderList" items={['Read the release notes for removed APIs', 'Upgrade the control plane, API server first', 'Drain one stall', 'Upgrade that stall’s kubelet', 'Uncordon it, then do the next stall']} label="First step at the top" success="That is the safe order. One stall at a time, so lunch keeps going." />
</Card>

<Card id="predict" type="predict">

<Card id="deeper" type="deeper">
Each minor gets about a year of patches. Managed clouds can upgrade the control plane for you. You still check your YAML first. Self-built clusters use tools like `kubeadm upgrade`. In-place minor kubelet upgrades are not supported: drain the stall first.
</Card>
