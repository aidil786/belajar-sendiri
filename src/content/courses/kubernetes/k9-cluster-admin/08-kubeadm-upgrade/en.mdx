The office’s version lives in its static pod files. A **<Term id="kubeadm-upgrade">kubeadm upgrade</Term>** writes new image tags there. One minor version per step.

<Card id="try-order" type="try">
Put the office’s upgrade in order, like the official kubeadm steps.

<Interactive name="OrderList" items={['Install the new kubeadm (1.37.x)', 'sudo kubeadm upgrade plan', 'sudo kubeadm upgrade apply v1.37.x', 'kubectl drain the control-plane node', 'Install the new kubelet and kubectl, restart the kubelet', 'kubectl uncordon the control-plane node']} label="First step at the top" success="That is the office routine. New tool first, then look, then change." />

<Hint>kubeadm upgrades the office. The kubelet is a separate package, so it comes after.</Hint>
</Card>

<Card id="predict" type="predict">

<Card id="try-build" type="try">
Your practice office runs v1.37.0. Build the command that moves it to the patch v1.37.2.

<Interactive name="CommandBuilder" pieces={[{ text: 'sudo', means: 'as root' }, { text: 'kubeadm', means: 'the tool that built the cluster' }, { text: 'upgrade', means: 'renovate' }, { text: 'apply', means: 'do it now, on the first control-plane node' }, { text: 'v1.37.2', means: 'the target version' }]} decoys={[{ text: 'v1.39.0', means: 'two minors ahead: not allowed' }, { text: 'node', means: 'for the other nodes, after the first one' }]} success="That is the command. It changes the whole office, so back up etcd first." />

`apply` rewrites the office. Danger: take an etcd snapshot before it.
</Card>

<Card id="deeper" type="deeper">
Other control-plane nodes and the workers run `sudo kubeadm upgrade node` instead of apply. kubeadm also renews its certificates on upgrade. It keeps backups under `/etc/kubernetes/tmp`. Our practice terminal shows a real `kubeadm upgrade plan` on dev-control-plane. It was recorded on a kind cluster. It can’t run apply.
